What we can see — Undercut

A licence check, not telemetry.

Privacy already says the free skill sets no cookies, runs no analytics, and doesn't phone home — that's still true, and it's the whole story for Free. Pro adds exactly one network thing: your machine periodically fetches a signed policy file so its tier→model map stays current. That fetch is an entitlement check — proving your account is still paying — not a report on what you're working on. This page is the honest, specific account of what that check reveals, what it never sees, and how long we keep it.

What an authenticated policy fetch reveals

When a paired Pro machine syncs, our servers see exactly four things, because they're what any authenticated HTTP request necessarily carries:

  • Account ID — which subscription is asking.
  • IP address — where the request came from, the way any server sees any request's source.
  • Timestamp — when the request happened.
  • Current policy version — which revision of the policy file your machine already has, so we know whether to send a diff or say "no changes."

That's the complete list. Nothing else is in the request, and nothing else is logged from it — see the allowlist note below.

Why this is categorically different from telemetry

"Telemetry" in the sense our other pages rule out means data about your work: prompts, code, file paths, repo names, what task you ran, how it went. A policy fetch carries none of that — it's the same shape of signal any paid product's server needs to answer "is this account still entitled to what it's asking for," the way a license server, an app store receipt check, or a subscription paywall works. It's unavoidable for any authenticated request to any server, and it's a genuinely different thing from watching what you build. We think a skeptical reader is right to notice the gap between "nothing leaves your machine" (true of Free) and "an authenticated fetch happens" (true of Pro) — so this page draws that line explicitly instead of leaving it for someone else to find.

What a fetch never contains

The policy endpoint's request logging runs off an explicit allowlist, the same pattern /api/lead already uses for form submissions — only named fields are ever written, nothing is captured by default. Specifically never logged or transmitted: prompts, code, file contents, file paths, working directory, repo name, session content, the User-Agent string, or which coding agent you're running. A sync is never correlated to a coding session, and the server has no way to tell "you ran a task" from "your clock rolled past the refresh interval" — those look identical from our side, which is the point.

Retention

Raw access logs (account ID, IP, timestamp, policy version) are kept 30 days, then deleted. After that window, only aggregate, non-per-account counters survive — total sync volume, for capacity planning — never a per-user timeline you could reconstruct someone's activity from. We don't keep a standing log of when any one account has synced beyond that 30-day window.

What a proxy does vs. what Undercut does

"Proxy" gets used loosely for anything that touches model routing, so here's the specific comparison. A proxy sits in your request path and brokers every call live; Undercut's mechanism is a periodic pull of a signed config file that your local agent reads and applies itself.

QuestionA live routing proxyWhat Undercut does
Sees each prompt/response?Yes — it's in the request pathNo — dispatch decisions happen locally, in the agent, from the policy file already on disk
Brokers your live model traffic?Yes — every call passes through itNo — your agent talks to your model provider directly; Undercut never sits between you and it
What actually crosses the network to us?Every request and response bodyOnly a periodic pull of a small signed policy file (account ID, IP, timestamp, version — see above)
If it goes down mid-session?Every in-flight call breaks — it's a single point of failureNothing breaks. The agent keeps using the last cached policy file; nothing was ever waiting on a live answer
If the vendor disappeared entirely?Routing stops working — there's no traffic path without itThe last cached policy.json keeps working indefinitely; failing that, it falls back to the free static models.md map. Dispatch never depends on us being reachable

Same point pricing already makes about the mechanism itself: nothing decides per call on the network path — still not a proxy.

Sync cadence is local, client-initiated, and optional

The default is a daily check, but "daily default" describes a client-side timer, not a service watching you. There is no resident daemon on our end or yours — your machine's own process wakes up, checks whether the cached policy is past its TTL, and if so makes one outbound request; if you never run the client, nothing calls out at all. Nothing about that mechanism requires the daily default:

  • Slow it down. Set a longer TTL and sync weekly, monthly, or on whatever cadence you want.
  • Disable it. Turn sync off entirely; the last cached policy keeps being used until you turn it back on.
  • Run fully offline, indefinitely. Download the signed policy bundle once and drop it in place by hand — the same signature verification applies, there's just no periodic fetch at all.
